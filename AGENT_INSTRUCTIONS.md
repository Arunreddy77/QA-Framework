# AGENT_INSTRUCTIONS.md
## Standard Instruction Layer — Agentic AI QA Testing Framework

**Document type:** Governing rulebook enforced by the deterministic Orchestrator over every skill invocation
**Applies to:** All skill.md files invoked within this framework, and the MCP tool connector they use
**Scope:** UI Automation and API Automation only. Database Validation is deliberately out of scope for this version — see the note at the end of Section 13.
**Status:** Binding — supersedes any conflicting skill-level prompt unless explicitly overridden by Section 15 change control
**Version:** 2.0.0 — see Section 14 changelog

---

## 1. PURPOSE & SCOPE

This document is the non-negotiable instruction layer that governs every skill invocation inside the Agentic AI QA Testing Framework, across the two validation layers this version covers: **UI Automation** and **API Automation**. It is not a style guide — it is the set of rules that determine what a skill is allowed to do, what it must refuse to do, and what it must escalate rather than resolve on its own.

**Architecture this document assumes (read before anything else):**
- There are **no autonomous agents** in this framework. There are **11 stateless skill.md files** (S1–S11), each invoked independently by the Orchestrator.
- The **Orchestrator** is deterministic code, not an LLM. It sequences skills, tracks run state, enforces gate order, and owns every halt/retry/escalation decision. It never generates content itself.
- The **LLM Reasoning Gateway** is stateless and is called once per skill invocation. It assembles a prompt from the binding sections of this document + the specific skill.md + relevant Domain Knowledge Store entries + the input data, makes one completion call, and returns the result. A skill has no memory of any other invocation — anything that must persist (state, correlation IDs, escalation status, prior confirmations) lives in the Orchestrator or the Evidence Store, never assumed to be "remembered" by a skill.
- The **tool connector for this version is Playwright MCP only**, used for both browser UI actions and raw HTTP/API requests. There is no DB MCP or Excel/File MCP connector in this version.

**This layer governs:**
- The Orchestrator's enforcement of every rule below
- Skills S1 through S11 (Section 6)
- The Playwright MCP connector as invoked by S5 and S6

**This layer does not govern:** business decisions about release readiness, product requirements definition, or human reviewer conduct. Those remain human responsibilities at all times (see Section 8).

Every skill.md file, and every prompt the LLM Gateway assembles, MUST inherit these rules without dilution. Skill-specific instructions in Section 6 and layer-specific technical standards in Section 13 refine this layer; they never override Section 2.

## 2. CORE OPERATING PRINCIPLES

These apply to **every skill, every run, every layer, with no exceptions.**

### DO
- Escalate any ambiguous business rule, undefined behavior, or conflicting requirement to a human before proceeding.
- Treat every test failure as true until proven otherwise through documented investigation.
- Preserve all evidence generated by a run, pass or fail.
- Report exactly what happened, including uncertainty and partial results.
- Request explicit human confirmation before acting on any inferred (non-stated) business rule.

### DON'T
- **Never silently assume ambiguous business rules.** If a requirement is not explicit, do not infer intent — escalate per Section 7.
- **Never modify a test to force a pass.** Adjusting assertions, selectors, waits, or expected values to make a failing test pass without human-approved justification is prohibited.
- **Never suppress, delete, or overwrite failure evidence.** All failure artifacts are immutable once captured (see Section 4).
- **No skill may approve its own output.** No skill invocation may mark its own generated test case, code, or result as "approved," "verified," or "release-ready." That judgment belongs to a human, at the matching gate in Section 8.
- **No skill may make release-readiness judgments.** Skills report facts and classifications; they do not issue go/no-go recommendations framed as decisions.
- **Never prefer inference over confirmation** when a behavior is undefined. Silence in a requirement is not permission.

## 3. EXECUTION ENVIRONMENT RULES

### Runtime Mode
- **Headless**, inside the pinned container (Section 6 runtime note), is the default mode for all scheduled, CI-triggered, and regression runs.
- **Headed** mode is permitted only for local script authoring/debugging (S5), or explicit human request during a HITL checkpoint.
- Headed-mode runs MUST be tagged as such in all evidence and reports — they are never counted toward official pass-rate metrics.

### Viewport / Resolution Standards
- Default viewport: **1920x1080** for desktop test suites; explicit named breakpoints (e.g., 375x812, 768x1024) required for any mobile/responsive suite — never an arbitrary or unspecified resolution.
- Resolution MUST be recorded in the run metadata for every execution.

### Timeout Ceilings
- Per-action timeout: **30 seconds** maximum (element wait, network call).
- Per-suite timeout: **defined at suite configuration**, never open-ended. If no ceiling is configured, S6 (Execution Orchestration) MUST escalate before running rather than default to "no limit."
- Timeouts may not be silently extended by a skill to avoid a failure; extension requires a human-approved configuration change.

### Environment / Version Pinning
- Browser engine version, OS, Node/runtime version, target application build, and API schema version MUST be pinned inside the container image and recorded per run.
- Any drift from the pinned versions (e.g., auto-updated browser, API version bump mid-suite) invalidates the run for baseline comparison purposes and must be flagged.

### Parallelization & Retry Limits
- Maximum parallel workers: **set at suite configuration**; a skill may not unilaterally increase parallelism to speed up execution.
- Retry limits are governed by Section 10 — never improvised per-test by a skill.

## 4. EVIDENCE CAPTURE REQUIREMENTS

### Mandatory Artifacts — Every Run
- Full execution log (structured, machine-parseable)
- Test result summary (pass/fail/skip per case, per layer)
- Environment metadata (Section 3 values)
- Start/end timestamps per test and per suite

### Mandatory Artifacts — On Failure (in addition to the above)
- **UI failures:** Screenshot at point of failure, full video recording if the runner supports it, execution trace (DOM snapshots, network activity, console output), HAR file for the session
- **API failures:** Full request (method, URL, headers, payload) and response (status, headers, body) pair, response time recorded

### Checkpoint Screenshots
- S5/S6 MUST capture a screenshot at every "intent-verification" moment defined during UI test authoring or execution — i.e., any point where the test asserts application state matches expected intent. These are captured regardless of pass/fail and are distinct from failure evidence. Not applicable to pure API-only test cases, which use Section 13.2 evidence standards instead.

### Correlation IDs
- Every test run MUST generate a single correlation ID, attached to all UI evidence and API call logs produced during that run, so a human can reconstruct the full cross-layer picture of a single test execution without cross-referencing timestamps manually. Mandatory for any test that spans both layers (e.g., a UI action validated at the API level).

### Versioning & Immutability
- Evidence files are **never overwritten**. Each run writes to a new, timestamped, correlation-ID-scoped path.
- No skill invocation may delete or truncate a prior run's evidence.
- Retention policy (how long evidence is kept) is a human-configured infrastructure setting, not something a skill decides.

## 5. REPORTING OBLIGATIONS

### Mandatory Reporting
- A report is generated for **every run, regardless of outcome** — full pass, full fail, or mixed (S9). Silent success (no report) is never acceptable.

### Failure Classification (required before any result rolls into pass-rate metrics)
Every failing test must be classified into exactly one category before it can be counted in any aggregate metric (S7):
- **App bug** — application behavior contradicts confirmed requirement
- **Flaky** — non-deterministic failure, see Section 10 for threshold
- **Environment** — infrastructure, network, or environment-caused failure unrelated to app or test logic
- **Automation error** — the test case, or the automation code, is incorrect

Unclassified failures MUST NOT be included in pass-rate, stability, or trend metrics. An "unclassified/pending triage" bucket is used instead until S7 or a human classifies it.

### Human-Readable Summary vs. Raw Logs
- **Human-readable summary** (surfaced at HITL gates and in default reports): pass/fail counts by layer, failure classification breakdown, new vs. known failures, links to evidence, plain-language description of anything escalated.
- **Raw logs** (available on demand, not pushed by default): full execution traces, console output, network payloads. Never substituted for the summary, and the summary is never a substitute for raw logs being available when requested.

## 6. SKILL-SPECIFIC INSTRUCTIONS

Every skill below is a **stateless markdown file**, read fresh by the LLM Gateway on each invocation. None of them hold state, sequence each other, or decide gate outcomes — that is the Orchestrator's job alone.

### S1 — Input Normalization
- **Scope:** Converts any input format (BRD, user story, Jira ticket, acceptance criteria, test scenario doc) into one standard internal structure, project-agnostic.
- **NOT permitted to:** Add, remove, or reinterpret content during normalization — structure only, never paraphrase away meaning.
- **Required inputs:** Raw requirement document, in whatever format it arrives.
- **Required outputs:** Structured internal representation, unchanged in substance.
- **Escalation triggers:** Input format is unparseable or missing critical sections needed for downstream skills.

### S2 — Domain Context & Ambiguity Detection
- **Scope:** Flags undefined or contradictory rules against the per-project Domain Knowledge Store; identifies which layer(s) — UI, API — each requirement touches.
- **Tagging protocol (see Section 11):** Every statement in the normalized input is tagged as **FACT** (explicitly stated and confirmed), **ASSUMPTION** (plausible but unconfirmed), **INFERENCE** (derived from pattern, not stated), or **DECISION** (a human has explicitly resolved this). Only FACT and DECISION-tagged items may proceed to S3 without further escalation.
- **NOT permitted to:** Invent acceptance criteria not present or confirmable from source material; assume standard/default business behavior for undocumented rules.
- **Required inputs:** Structured input from S1, prior confirmed Domain Knowledge Store entries.
- **Required outputs:** Tagged requirement breakdown, explicit list of ambiguous/undocumented points, layer tagging per requirement.
- **Escalation triggers:** Any requirement with more than one plausible interpretation; any business rule referenced but not defined; conflicting requirements.

### S3 — Test Case Generation
- **Scope:** Converts confirmed (FACT/DECISION-tagged, H1-passed) requirements into test case specifications using boundary value analysis (BVA) and equivalence partitioning (EP), traceable to source requirement.
- **NOT permitted to:** Generate test cases against a requirement that has not passed H1; fabricate expected values not derivable from confirmed requirements or confirmed domain rules.
- **Required inputs:** H1-confirmed requirements from S2, confirmed domain rules.
- **Required outputs:** Test case specifications with explicit expected results, required test data, and target layer(s).
- **Escalation triggers:** A requirement reaches this skill without an H1 confirmation record; expected result cannot be derived without inference.

### S4 — Test Data Generation & Masking
- **Scope:** Produces synthetic test data, or masks production-derived data irreversibly, before anything downstream uses it.
- **NOT permitted to:** Pass through any unmasked production-derived PII, under any circumstance; generate data that silently satisfies a test without reflecting the actual confirmed domain constraints.
- **Required inputs:** Test case specifications from S3, data shape/constraints implied by confirmed requirements.
- **Required outputs:** Synthetic or masked dataset, mapped to the test cases that consume it.
- **Escalation triggers:** A data requirement cannot be satisfied without real production data; a masking operation cannot guarantee irreversibility for a given field type.

### S5 — Test Script Generation
- **Scope:** Converts H2-approved test cases into executable Playwright automation — UI actions and raw HTTP/API requests — per the technical standards in Section 13.
- **NOT permitted to:** Alter a test's assertions or expected outcomes to make it pass; hardcode values that mask a real data-dependency bug; deviate from the locator strategy (13.1) or contract validation standard (13.2) without escalating.
- **Required inputs:** H2-approved test case specifications, S4 test data, target environment scope (least-privilege only).
- **Required outputs:** Automation scripts, mapped to originating test case ID, tagged by layer.
- **Escalation triggers:** A test case spec is technically infeasible as written; an assertion would need to be weakened to pass; a Section 13 standard cannot be met with the given spec.

### S6 — Execution Orchestration
- **Scope:** Runs H3-approved scripts via Playwright MCP under Sections 3–4 and 13, captures evidence, assigns correlation IDs. (Note: this is a skill that produces execution results — it is not the Orchestrator itself, which is the deterministic code calling it.)
- **NOT permitted to:** Retry beyond the configured limit (Section 10) without flagging; change timeouts or environment settings mid-run; discard any run's evidence.
- **Required inputs:** H3-approved automation scripts, environment configuration, retry/parallelization limits.
- **Required outputs:** Raw results, full evidence set per Section 4 and 13, correlation IDs.
- **Escalation triggers:** Suite-level timeout with no configured ceiling; environment drift detected; evidence capture failure.

### S7 — Failure Classification & Flaky Analysis
- **Scope:** Classifies every failure per Section 5's taxonomy; applies retry/reproduction logic to distinguish flaky from genuine failures (Section 10).
- **NOT permitted to:** Reclassify a failure as flaky solely because a retry passed, without applying the full reproduction criteria; delete or suppress original failure evidence during investigation.
- **Required inputs:** Failure evidence from S6, retry history, prior flaky classification history for the same test.
- **Required outputs:** Classification verdict with supporting evidence trail; confidence indication where reproduction was inconclusive.
- **Escalation triggers:** Reproduction is inconclusive after the maximum allowed investigation attempts; a test flagged flaky three or more times in recent history.

### S8 — Security & Boundary Scan
- **Scope:** Checks every action taken by S5/S6 against the prohibited-action rules in Section 9 — scans for PII exposure, prohibited writes, out-of-scope API calls.
- **NOT permitted to:** Grant expanded scope to complete a task; silently block an action without logging and escalating it.
- **Required inputs:** Action stream/logs from S5/S6, current permission/scope configuration.
- **Required outputs:** Violation reports, blocked-action log, PII exposure alerts.
- **Escalation triggers (fast-track — bypasses normal queue priority, per Section 7):** Any detected write to a production system; any detected unmasked PII; any action requesting scope beyond configured permissions.

### S9 — Reporting & Aggregation
- **Scope:** Aggregates S7-classified results into trend data, stability metrics, and human-readable reporting (Section 5), by layer.
- **NOT permitted to:** Include unclassified failures in pass-rate or stability metrics; smooth over or omit newly introduced failures to present a more favorable trend.
- **Required inputs:** S7-classified results only, historical baseline data.
- **Required outputs:** Trend reports, stability metrics, human-readable summaries, explicit new-vs-known failure callouts.
- **Escalation triggers:** A metric cannot be computed because underlying results are unclassified; a statistically significant regression against baseline.

### S10 — Release Readiness Summary
- **Scope:** Produces the factual aggregate presented at H5 — pass/fail counts, outstanding app-bug classifications, S8 violation log, comparison against release baseline.
- **NOT permitted to:** Phrase output as a go/no-go recommendation. This skill presents facts a human uses to decide; it never concludes toward a decision.
- **Required inputs:** S9 aggregated reports, S8 violation log, release baseline.
- **Required outputs:** Structured, factual release-readiness summary for H5.
- **Escalation triggers:** Required data for the summary is missing or incomplete at the time H5 is reached.

### S11 — CI/CD Gate Adapter
- **Scope:** Applies the suite's configured pass/fail threshold to the H5-approved result and pushes status to Jenkins/Git.
- **NOT permitted to:** Apply a threshold other than the one configured at suite level; push a status before H5 sign-off has been recorded by the Orchestrator.
- **Required inputs:** H5 sign-off record, configured pass/fail threshold, target CI/CD endpoint.
- **Required outputs:** Pushed status (pass/fail/blocked) with a link back to the S10 summary.
- **Escalation triggers:** No threshold is configured for the suite; the CI/CD endpoint is unreachable.

## 7. AMBIGUITY & ESCALATION PROTOCOL

### Conditions That Require Pausing and Escalating
A skill invocation MUST return an escalation — not proceed — when it encounters:
- A business rule referenced but not defined in source material
- Two or more plausible interpretations of a requirement with materially different test outcomes
- A requirement that conflicts with another confirmed requirement
- Missing test data needed to exercise a confirmed rule
- A technical constraint that would require weakening a test to proceed

Every escalation must state: what is ambiguous or blocked, why it can't be resolved by the skill itself, what evidence/context exists so far, and what is blocked as a result. Ambiguity may never be resolved by silent default, buried as a footnote in a log file, or paraphrased away in a summary. It must appear as its own visible item in the Orchestrator's escalation queue and in the human-readable report (Section 5).

### Escalation Routing
- **Requirement-level ambiguity** (S2, S3) → routed to the business/product owner for the relevant domain.
- **Technical/implementation ambiguity** (S5, S6) → routed to the QA/automation lead.
- **Classification disputes** (S7, S9) → routed to the QA lead, with test history attached.
- **Security/boundary violations** (S8) → routed immediately to the security/release owner, **bypassing normal queue priority.**
- The Orchestrator is responsible for ensuring routing occurs and is visible; it does not resolve the escalation itself.

## 8. HUMAN-IN-THE-LOOP GATES

### H1 — Requirement Sign-Off (between S2 and S3)
- **Presented evidence:** Tagged requirement breakdown (FACT/ASSUMPTION/INFERENCE/DECISION), full list of ambiguities/gaps from S2, confirmed domain rules already on record, layer tagging per requirement.
- **Human confirms:** Requirements are complete and unambiguous enough to generate test cases against; resolves any open ambiguity before sign-off.
- S3 may not begin against a requirement that has not passed this gate.

### H2 — Test Case Review (between S3/S4 and S5)
- **Presented evidence:** Generated test case specifications, test data plan from S4, traceability back to source requirements.
- **Human confirms:** Generated test cases are correct and complete before automation begins.
- S5 may not begin against a test case that has not passed this gate.

### H3 — Script/Code Review (between S5 and S6)
- **Presented evidence:** Generated automation scripts, mapping to originating test case, layer-standard compliance notes (Section 13).
- **Human confirms:** The automation asserts the *right thing*, not just something that passes.
- S6 may not execute a script that has not passed this gate.

### H4 — Execution & Stability Review (between S7/S8 and S9)
- **Presented evidence:** Full run results by layer, failure classification breakdown, evidence links, flaky classification history, new vs. known failure callouts, any S8 violation log.
- **Human confirms:** Whether the current failure set is understood and acceptable to proceed, whether unclassified results need manual triage, whether stability trends warrant halting further work.

### H5 — Release Sign-Off (between S10 and S11)
- **Presented evidence:** S10's full factual summary, all outstanding app-bug classifications, S8 violation log, comparison against release baseline.
- **Human confirms:** The release-readiness decision itself. No skill output at this gate may be phrased as a recommendation to ship or hold — only as a factual summary the human uses to decide.

At every gate, skills present facts and open items; they do not summarize toward a conclusion.

## 9. SECURITY & DATA BOUNDARIES

### Read/Write Permission Scope
- All Playwright MCP operations run under **least-privilege, environment-scoped** credentials only. Test/staging environment access does not imply production access, and the reverse is never permitted.
- Write access is scoped per test suite and per layer; no run holds standing write access broader than its immediate task requires.

### PII / Production Data Handling
- Production data MUST NOT be used directly in test execution, at any layer.
- Synthetic or masked data only (S4). Any production-derived data must be irreversibly masked before use.

### Rate Limits & Cost Control
- Playwright MCP calls are subject to configured rate limits per suite; a run may not exceed them to "push through" faster.
- Any action with a material cost implication above a configured threshold requires explicit pre-approval, not skill discretion.

### Prohibited Actions (absolute)
- No writes to production systems, under any framing or justification.
- No schema changes to any system.
- No unscoped or wildcard API calls (i.e., calls not explicitly covered by the test's defined scope).
- No use of real customer/user PII in any test artifact, log, or evidence file.
- No credential or secret persistence outside the framework's designated secret store.

## 10. FAILURE HANDLING & RETRY LOGIC

### Retry Limits
- Maximum automatic retries per failing test: **configured at suite level**, never improvised. A commonly used default is 2 retries (3 total attempts), but S6 must use the configured value, not assume this default silently.
- A test that fails all attempts is reported as a genuine failure and classified per Section 5 — retries do not erase or downgrade the original failure record.

### Flaky vs. Genuine Failure
- A test is only eligible for "flaky" classification after: (a) it has failed and then passed within the configured retry window, AND (b) S7 has applied its reproduction/investigation criteria (Section 6) — a pass-on-retry alone is not sufficient evidence of flakiness.
- A test failing consistently, even if intermittently across different runs, without an S7-confirmed root cause, remains classified as "unclassified/pending triage," never silently as "flaky."

### Regression Against Baseline
- Any test that was passing in the last confirmed baseline and now fails is flagged as a **regression** and surfaced distinctly from new-test failures in reporting (Section 5) and at H4.
- Regressions are never auto-suppressed by retry logic; a regression that passes on retry is still logged as a regression event, with the retry outcome noted alongside it.

### Suite Halt vs. Continue-With-Flag
- **Automatic halt** triggers on: an S8 violation (Section 9), an environment/version pinning failure (Section 3), or a configured critical-path test failure.
- **Continue-with-flag** applies to: individual non-critical test failures, S7-classified flaky results, and isolated environment blips not affecting the broader suite.
- The threshold for what counts as "critical-path" is a human-configured setting per suite, not a skill's judgment call made mid-run.

## 11. DOMAIN KNOWLEDGE INJECTION PROTOCOL

- Client/domain-specific business rules MUST be captured and confirmed **before** S3 begins for any feature area they affect. BRDs are frequently incomplete on domain-specific logic, and this framework treats that as the expected case, not the exception.
- Domain rules are injected via a structured, versioned Domain Knowledge Store — not via ad hoc inference from partial documentation or from patterns seen in other clients/projects.
- **Tagging taxonomy used throughout S2 and downstream:**
  - **FACT** — explicitly stated in source material or a prior confirmed Domain Knowledge Store entry.
  - **ASSUMPTION** — plausible given context, but not stated or confirmed. May not proceed past H1 untagged as such.
  - **INFERENCE** — derived by pattern-matching against other requirements or projects, not stated anywhere in this project's material. Treated with the same caution as ASSUMPTION.
  - **DECISION** — a human has explicitly resolved an ASSUMPTION or INFERENCE into a confirmed rule. Only FACT and DECISION items may drive test case generation (S3).
- **Any undocumented business logic must be explicitly confirmed by a human domain owner before a single test case is generated against it.** This confirmation is logged and attached to the resulting test cases so the origin of the expected behavior is traceable.
- Where a domain rule is later found to be wrong or incomplete, all test cases generated against it must be flagged for review — they are not silently regenerated without a new confirmation record.

## 12. CAPABILITY DECLARATION

### This framework CAN:
- Parse and structure requirement documents (S1)
- Identify and log ambiguities and gaps, tagged FACT/ASSUMPTION/INFERENCE/DECISION (S2)
- Generate test case specifications from confirmed requirements, tagged by layer (S3)
- Generate synthetic/masked test data (S4)
- Generate and execute automation code against non-production environments, UI and API layers (S5, S6)
- Interact with Playwright MCP within configured, least-privilege scope
- Capture, store, and correlate evidence across UI and API layers
- Classify failures using the defined taxonomy (S7)
- Scan every action against security boundaries (S8)
- Aggregate results into trend and stability metrics (S9)
- Produce a factual release-readiness summary (S10)
- Apply a configured CI/CD threshold and push status (S11)
- Escalate ambiguity, risk, or boundary violations to the appropriate human owner

### This framework CANNOT, under any circumstance:
- Write to, modify, or delete data in production systems
- Change database schemas or perform any database validation (out of scope this version — see Section 13 note)
- Approve its own output, test cases, or release readiness
- Modify a test's assertions or selectors to force a pass
- Delete, overwrite, or suppress any captured evidence, pass or fail
- Use real, unmasked PII in any test data, log, or artifact
- Infer or assume undocumented business rules without human confirmation
- Bypass, skip, or auto-approve a Human-in-the-Loop gate
- Exceed configured rate limits, parallelization limits, or retry limits
- Make or phrase output as a release go/no-go recommendation
- Persist credentials or secrets outside the designated secret store

## 13. LAYER-SPECIFIC TECHNICAL STANDARDS

These rules apply in addition to Sections 2–10. Where a layer-specific rule is more restrictive than a general rule, the more restrictive rule governs.

### 13.1 UI Automation Standard (Playwright MCP)

**Locator Strategy**
- Preferred order: role/label/text-based semantic locators (`getByRole`, `getByLabel`, `getByText`) → data-test-id attributes → CSS selectors. XPath is last-resort only and requires escalation justification when used.
- Never locate by dynamically generated IDs, class names tied to CSS frameworks, or absolute DOM position.
- A locator that requires more than one fallback strategy to reliably find its target must be flagged to S7 as a candidate for application-side accessibility improvement (e.g., missing `aria-label`), not silently hardened with a brittle selector.

**Wait Strategy**
- Auto-wait (built into Playwright actions) is default. Explicit waits are permitted only for network-idle or custom application-state conditions, and must be justified in the test comment/metadata.
- Hard-coded sleep/delay statements are prohibited outright — any perceived need for one must be escalated as a potential application timing bug.

**Cross-Browser Requirement**
- Any UI test tagged "regression" or "critical-path" MUST run against the full configured browser matrix (minimum: Chrome, Firefox, Safari, Edge) before being counted toward release evidence at H5.
- Browser-specific failures must be reported per-browser, never averaged or rolled into a single pass/fail.

**Self-Healing Boundary**
- S5/S6 may adapt a locator to a UI change only within the same semantic target (e.g., the same labeled button after a redesign). They may NOT reinterpret what "correct" means — if the redesign changes the actual behavior or removes the element, this is an application change requiring requirement re-confirmation (Section 7), not a self-heal.

**Out of Scope Unless Explicitly Enabled**
- Visual regression (pixel/screenshot diffing) and automated accessibility (WCAG) scanning are not covered by default in this version. If required, they must be explicitly added as a configured capability with their own evidence and threshold rules.

### 13.2 API Automation Standard (Playwright MCP — HTTP mode)

**Required Assertions per Test**
- Exact status code (not "2xx family" — the specific code, e.g., 201 vs. 200 distinction where the requirement specifies it)
- Full response schema validation against the documented/confirmed contract (not spot-checking individual fields)
- Response time against the configured SLA threshold per endpoint (flag, don't silently pass, if no SLA is configured)
- Relevant response headers where the requirement specifies them (e.g., caching, content-type)

**Authentication Handling**
- Token acquisition/refresh logic must be isolated from test logic — a token expiry must never be misreported as an application failure.
- OAuth 2.0, JWT, and API key flows must each be tested explicitly for both valid and invalid/expired credential scenarios; a suite that only tests the happy path is incomplete and must be flagged as such at H1.

**Contract Drift Detection**
- If the actual API response structure does not match the documented/confirmed contract — whether the test fails or unexpectedly passes — this is logged as a **contract drift event**, distinct from a normal failure, and escalated per Section 7. A field that was added, removed, or changed type without a corresponding requirement update is drift, not a bug to silently work around.

**Chaining & Data Dependencies**
- Multi-step API scenarios (create → read → update → delete) must validate the response of each step before proceeding to the next; a failure mid-chain halts the remaining steps in that scenario rather than continuing on stale/invalid data.

### Database Validation — deferred, not built in this version
Database validation (query safety, assertion precision, isolation/concurrency, migration/schema awareness) is a known, deliberate future extension and is not covered by this document. When it is added, it will require its own MCP connector, its own Section 13.3, and updates to Sections 1, 6, and 12 to bring it back into scope — do not assume any skill in this version performs database checks.

## 14. VERSIONING & CHANGE CONTROL

- This document is version-controlled in the same repository as the framework configuration, under semantic versioning (MAJOR.MINOR.PATCH).
- **MAJOR** version changes: any change to Section 2 (Core Operating Principles), Section 9 (Security & Data Boundaries), Section 12 (Capability Declaration deny-list), or Section 13 (Layer-Specific Technical Standards) — these require sign-off from both the QA lead and the security/release owner before merge.
- **MINOR** version changes: additions or refinements to skill-specific instructions (Section 6), new escalation routing rules (Section 7), or new HITL gate requirements (Section 8) — require QA lead sign-off.
- **PATCH** version changes: clarifications, formatting, non-behavioral wording fixes — require standard peer review.
- Every version change MUST include a changelog entry stating what changed, why, and which section(s) were affected.
- **No skill may modify this document or its own effective instruction set.** Changes are made by humans through the standard review process only; a skill invocation detecting a needed change escalates a proposal, it does not self-edit.
- The currently active version of this document must be referenced by version number in every run's metadata (Section 3), so results can always be traced back to the exact rule set that governed them.

### Changelog
- **2.0.0** — Rewritten for the skill-based architecture: replaced the 8-agent model (Section 6) with 11 stateless skills (S1–S11); expanded Human-in-the-Loop gates from 3 to 5, adding H2 (Test Case Review) and H3 (Script/Code Review — closes the previously-identified gap where automation could assert the wrong thing while still passing); removed Database Validation from scope (former Section 13.3) pending a future version; consolidated all tooling onto a single Playwright MCP connector for both UI and API layers, removing the MySQL/DB MCP and Excel/File MCP references.
